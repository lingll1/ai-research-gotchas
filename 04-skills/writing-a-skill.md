# 写一个能被正确触发的 skill

> skill 的正文写得好不好，只影响"用到时管不管用"；**描述写得好不好，决定它会不会被用到**。

## 现象

写了一个很用心的 skill，检查清单齐全、命令都能跑。结果是：

- **该用的时候从没被调用过**
- 不该用的时候被反复调用（每次都很啰嗦，还答非所问）
- 一个 skill 越来越大，最后什么场景都往里塞，什么场景都不好用

## 根因

skill 是**两段被不同读者读的文字**：

| 部分 | 读者 | 用途 |
|---|---|---|
| 名称 + 描述（frontmatter） | **检索系统** | 决定"这次要不要加载它" |
| 正文（body） | **执行者（模型）** | 加载之后怎么做 |

绝大多数"skill 不生效"的问题，出在第一段 —— 描述写成了**内容摘要**，而不是**触发条件**。

模型在决定要不要用某个 skill 时，看到的是描述，看不到正文。如果描述写的是"本 skill 介绍 PowerShell 编码规范"，而用户问的是"为什么我的 .ps1 中文报错"，这俩在语义上离得很远。

## 做法

### 一、描述写"什么时候用"，不写"里面有什么"

**差的描述**（内容摘要式）：

```yaml
description: 记录 PowerShell 脚本编码与 BOM 的规范，包括 UTF-8、GBK、CRLF 等要点。
```

**好的描述**（触发条件式）：

```yaml
description: 当 PowerShell 脚本含中文导致语法报错、或需要生成 .ps1/.cmd 文件、
  或遇到 BOM/编码乱码问题时使用。含 UTF-8 BOM 与 GBK 解码的诊断步骤。
```

区别在于**包含了用户真实会说的那些词**：`中文`、`报错`、`.ps1`、`乱码`。这些词是检索的锚点。

**实用技巧**：把你希望触发它的三句用户原话写进描述（可以略作概括），比如"脚本中文报错""BOM 是什么""生成 ps1 文件"。

### 二、名称用 kebab-case，说清领域

```
✅ powershell-encoding      ✅ docx-format-check      ✅ mcp-server-debug
❌ helper                   ❌ utils                  ❌ my-skill
```

名称是第二道检索信号。`helper` 这种名字等于放弃了这道信号。

### 三、正文：先给判断，再给命令

执行者拿到 skill 后，最需要的是**"现在该做哪一步"**，不是背景知识。推荐结构：

```markdown
# 标题（一句话说清这个 skill 解决什么）

## 什么时候用 / 什么时候别用     ← 边界先行，防止误用
## 判断步骤（先做什么，再做什么）
## 具体命令（可直接复制）
## 常见错误与对应处置
```

**把"别用"写在前面**，比写在最后有用得多。执行者往往只读开头。

### 四、写成"可执行"，不要写成"可阅读"

| 阅读友好（差） | 执行友好（好） |
|---|---|
| "应当注意编码问题" | "在写文件时用 `encoding=\"utf-8-sig\"`" |
| "需要验证字体是否嵌入" | "`pdffonts out.pdf`，看 `Em` 列是否为 `yes`" |
| "建议先备份" | "`Copy-Item x x.bak`，再做修改" |

**判断标准**：读者能不能不假思索地照着做。如果需要理解、推理、再决定，说明写得太抽象。

### 五、一个 skill 只干一件事

拆分信号：描述里出现了"以及""另外""还包括" → 大概率该拆。

一个 skill 覆盖 3 个场景的后果：描述必须写得很宽（触发不准），正文必须分叉（执行时要在里面找分支）。

**宁可三个小 skill，不要一个大 skill。**

### 六、渐进披露：把长内容推到附件

skill 正文过长会占满上下文，挤压真正的任务。做法：

```
skills/my-skill/
  SKILL.md          ← 主文件，只放判断与主路径（建议 100–200 行内）
  reference/
    edge-cases.md   ← 低频细节，主文件里用一行指向它
    examples.md
```

主文件里写："遇到 X 少见情况，读 `reference/edge-cases.md`"。
这样常规任务只加载主文件，罕见情况才按需展开。

## 边界

- 触发准确率不完全由描述决定，还取决于检索实现（关键词、向量、还是两者混合）。**在能测的环境里，写完后用几句真实的用户问法试一下**。
- 不是所有知识都该做成 skill。一次性的排查过程、只对一个项目成立的约定，写成项目内的文档比写成 skill 更合适。
- skill 数量多到一定程度，检索会互相干扰。**定期清理**：长期没被触发的，删掉或合并。
- 描述太长也会降低匹配质量。控制在 2–4 句、包含关键锚点词即可。

## 一句话记法

> **描述写给"要不要用它"的人看，正文写给"怎么用它"的人看。写反了，再好的 skill 也用不上。**
