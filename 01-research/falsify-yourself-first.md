# 先证伪自己，再怀疑环境

> 我曾经花了两个小时追一个"产品 bug"，最后发现是我的测试方法本身连不通。

## 现象

你改了一行代码 / 换了一个配置 / 加了一个参数，然后测试失败。第一反应通常是：

> "是不是这个东西本身有问题？"

然后开始读源码、翻 issue、换版本、重装依赖……两小时后发现：**测试脚本自己写错了。**

## 根因

**测试通路与被测对象共用了同一个假设。**

一个真实例子：某个本地服务监听 `127.0.0.1:3080`，监听正常。
我用 PowerShell 的 `Start-Job` 在这个地址上发请求，连不上。

推论链走偏成了：

1. `Start-Job` 连不上 → 看起来像端口没开
2. 检查端口 → 开着
3. 那就是服务没监听对 → 翻服务代码
4. 代码没问题 → 那是版本/权限/防火墙
5. ……两小时

**真相**：`Start-Job` 起的是**独立 PowerShell 进程**，它有自己的网络上下文与凭据上下文。用它在"本机回环地址"上验证另一个进程的服务，验证的是"第二个进程能不能连"，不是"服务在不在"。

换成在当前 shell 里直接 `Invoke-WebRequest` —— 通。

**两边都"看起来在测同一件事"，但它们不通用的前提不同。**

## 做法

### 一、动手前先问三个问题

1. **我的测试手段本身，有没有可能连不通？**（进程隔离、网络命名空间、权限、代理、DNS）
2. **如果被测对象完全正常，这个现象还会不会出现？**（会 → 说明现象不能证明 bug）
3. **有没有一个"绝对简单"的对照组？**

### 二、永远配一个对照组

不要只测"失败的路径"，同时测一条**必然成功的路径**：

```powershell
# 坏做法：只测目标
Invoke-WebRequest 'http://127.0.0.1:3080/health'

# 好做法：同一手段，测一个已知可用的目标
Invoke-WebRequest 'http://127.0.0.1:3080/health'   # 待测
Invoke-WebRequest 'http://127.0.0.1:3080/'         # 同服务，不同路径
Invoke-WebRequest 'http://127.0.0.1:7017/'         # 已知可用的另一服务
```

三条都失败 → 问题在**测试手段**或**网络层**，不在被测对象。
只有第一条失败 → 才开始怀疑接口本身。

### 三、把"现象"改写成"可证伪的命题"

| 烂命题 | 可证伪版本 |
|---|---|
| "服务挂了" | "在 shell A 中 `GET /health` 返回非 200" |
| "配置没生效" | "进程启动时间早于配置文件 mtime" |
| "代码有 bug" | "输入 X 时输出 Y，而规格书写的是 Z" |

第二种写法的好处：**你能直接设计一个实验去否定它。** 第一种只能靠猜。

### 四、区分"三种失败"

很多排查之所以乱，是因为把三种完全不同的失败混成一件事：

| 类型 | 表现 | 该查什么 |
|---|---|---|
| **没连上** | connection refused / timeout / DNS 失败 | 网络、端口、进程存活 |
| **连上了但被拒** | 401 / 403 / 412 | 凭据、UA、反爬、Referer |
| **连上了、成功了、但内容不对** | 200 但返回空壳 / 广告页 | 解析逻辑、JS 渲染、接口变更 |

**这三种要分开测。** 我见过最典型的误判是把"第三类"当成"第一类"，于是给一个本来能访问的站点判了"网络不通"的死刑，顺带把唯一可行的绕行路径也否掉了。

测**可达性**和测**可用性**是两个实验。

## 边界

- "先证伪自己"不等于无限自我怀疑。**给了对照组仍然失败，就该去怀疑被测对象了** —— 否则会陷入另一种空转。
- 这个原则对**已知稳定**的环境收益最大；对**全新环境**，先把环境摸清（版本、权限、网络出口）比证伪自己更优先。
- 有些坑确实是环境的（比如企业代理拦截、杀软注入）。所以结论要写成"在 X 条件下 A 失败、B 成功"，而不是"A 不行"。

## 一句话记法

> **先证明你的尺子没坏，再用尺子量东西。**
