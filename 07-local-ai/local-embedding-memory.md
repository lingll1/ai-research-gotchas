# 给 AI 的记忆库配一个本地小模型（512 维 embedding，22.9 MB，纯 CPU）

> 场景：AI 的长期记忆存在本地 SQLite 里，几千条。关键词检索（BM25）在"我记得有个关于 X 的事"这类查询上几乎失效。
> 结论先行：这里该装的是**embedding 小模型**，不是一个 LLM。装 LLM 会让检索变慢、变贵、变不可靠，而这活 23 MB 的模型就干得比它好。

## 现象

三个典型症状，都指向同一个根因：

1. **纯关键词检索，问法一变就崩**。库里明明有一条"后台脚本不能弹黑窗口"，查"静默运行"返回 0 条 —— 零字面重合。
2. **`status` 类命令说"可用"，但检索质量没变**。因为 `status` 字段恒为 `unknown`：它只查文件在不在，**不加载模型**，所以永远不会告诉你"能不能用"。
3. **迁移模型目录之后，明明成功了，自检却判定失败并自动回滚** —— 自检拿英文 `available` 去匹配 CLI 的中文输出「状态：可用」，还叠加了 UTF-8/GBK 乱码。

## 根因

- 记忆检索有两条通路：**词法**（BM25 / 倒排）和**语义**（向量近邻）。前者对精确名词强，后者对同义改写强，两者互补而不是替代。
- 语义通路需要一个 embedding 模型把文本压成定长向量。这件事的计算量是**一次前向**，不是生成，所以小模型（几千万参数）足够，且能在 CPU 上跑到毫秒级。
- 装一个 LLM 来"管理记忆"是把问题搞错了：LLM 擅长的是**读一批候选再判断**，不擅长给上千条记忆逐条算相似度。正确分工是 **小模型管召回，LLM 管最终的取舍与总结**。

## 做法

### 1. 选型：bge-small-zh-v1.5（量化 ONNX）

| 项 | 值 |
|---|---|
| 模型 | `Xenova/bge-small-zh-v1.5`（HuggingFace 上已转成 transformers.js 可用的 ONNX） |
| 权重 | `onnx/model_quantized.onnx`，**22.9 MB** |
| 输出维度 | **512** |
| 配套文件 | `config.json`、`tokenizer.json`（0.4 MB）、`tokenizer_config.json`、`special_tokens_map.json` |
| 运行时 | `@huggingface/transformers` 4.x + `onnxruntime-node`（CPU EP，不需要 CUDA） |
| 首次加载 | 440–470 ms；单条/批推理 0.3–0.9 s（含加载） |

选择理由：中文原生（不是英文模型硬套）、`small` 档在 CPU 上真的能跑、量化后 23 MB 可以跟着配置一起备份、512 维在几千条规模上内存与精度都够。

### 2. 用纯 ASCII 探针做验收，不要解析 CLI 的中文输出

这是整件事里最值钱的一条经验。

```js
// mneme-prodpath-check.mjs —— 走真实默认路径加载模型并推理，最后打一个纯 ASCII 标记
const { LocalEmbedder } = await import('<插件>/embed/local.js');
const e = new LocalEmbedder();          // 不传参 = 用生产默认目录
await e.init();
const v = await e.embed(['探针文本一', '探针文本二']);
console.log(`PROBE_OK dim=${v[0].length}`);
```

- 验收脚本只信一个**自己定义的、纯 ASCII 的、语义单一的**标记：`PROBE_OK dim=512`。
- 不要 `if (output.includes('可用'))`。中文输出在不同控制台代码页下会变成 `鍙敤` 一类的乱码，判定必然失败，而且失败得**静默且看起来像真的坏了**。
- 同理，`status` 里那些 `unknown` 字段一律不能当判据。

### 3. 迁移模型目录：junction，以及"DLL 常驻锁"这个硬墙

模型运行时是 600+ MB、4000+ 文件的目录树，通常想挪到非系统盘。会遇到一个非常具体的墙：

```
Remove-Item : 对路径 ...\onnxruntime.dll 的访问被拒绝
```

**根因**：`onnxruntime.dll`、`sharp-win32-x64.node`、`libvips-cpp.dll` 这类原生模块被宿主进程 **作为 DLL 常驻加载（mmap）**。Windows 不允许删除/移动已被映射的映像文件，`Access denied` 不是权限问题，是**内核拒绝**。改 ACL、用管理员、用 `robocopy /MOVE` 全都没用。

**做法**：必须先让宿主进程退出，再动手。

```powershell
# 1) 找出到底谁锁着（按模块名扫，别按进程名猜）
Get-Process | ForEach-Object {
    $p = $_
    try { $p.Modules | Where-Object { $_.FileName -like "$targetDir*" } | ForEach-Object {
        "PID=$($p.Id) $($p.ProcessName) <- $($_.FileName)" } } catch {}
}
```

```powershell
# 2) 优雅退出优先（CloseMainWindow → 宽限 → Stop-Process → 宽限 → -Force）
#    硬教训：强杀后冷启动 ~80 s，优雅退出 ~25 s。差 3 倍。
# 3) 确认无进程持有目标文件，再删本地副本、建链接
cmd /c mklink /J "C:\...\runtime" "D:\...\runtime"
```

- 用 **junction（目录联接）**而不是符号链接：junction 不需要开发者模式/管理员特权，且对普通子进程完全透明。
- 迁移后必须验证**透过链接能读到文件**，而不只是"链接对象存在"：

```powershell
# 别只看 LinkType，要真读一个字节
[System.IO.File]::OpenRead("C:\...\runtime\node_modules\onnxruntime-node\bin\napi-v6\win32\x64\onnxruntime.dll").ReadByte() | Out-Null
```

### 4. 检索质量怎么量，而不是"感觉变好了"

用库里真实的向量做对照，别用玩具数据：

- 对同一批查询，比较**向量 top5** 与 **BM25 top20** 的覆盖关系。
- 实测结论（真实记忆库、约 4300 条）：**向量 top5 里平均 40% 是 BM25 top20 完全没覆盖到的条目**。
- 例：查「硬盘坏了导致系统卡顿」，向量 top1 直接命中"系统盘 SSD 故障"那条；BM25 top1 跑偏到"自启动脚本"。
- 反例同样重要：查**具体名词**（函数名、专有名词、报错原文）时 BM25 更强。所以最终要**混合**，不是用向量替换 BM25。

### 5. 去重阈值的定法

如果记忆库要做去重归并，阈值不能拍脑袋：

| 余弦阈值 | 对数（本库实测） |
|---|---|
| ≥ 0.95 | 2 |
| ≥ 0.92 | 11 |
| ≥ 0.90 | 45 |
| **≥ 0.85** | **664（暴涨）** |

- 0.85 处从 45 跳到 664 —— 这是"话题集中型语料"的特征：同一主题的条目天然高相似。**0.85 在这个库里全是噪声**。
- 可信阈值取 **0.92**，且只处理**活跃条**（归档条不参与召回，动它没收益）。
- 相似度只是候选，最终判定仍要人（或 LLM）读一遍：本库 0.931 的两对里，一对是"2025 考研数据文件 vs 2026 真题"、一对是"六份必读 vs 五份必读" —— 数值几乎一样，语义完全不同。

## 边界

- **它不是 LLM，不会"管理"任何东西**。它只做一件事：文本 → 512 维向量。归并、改写、摘要仍然要 LLM 或人来做。
- **512 维 + small 档的上限**：长文档（>512 token）会被截断，跨语言检索弱，细粒度区分（同一主题下的细微差别）不如 1024 维 base 档。库里条目都是短文本，所以够用 —— 换成整篇文档检索就该升级模型。
- **向量只对新写入生效**：改模型、改维度、改切分方式之后，**历史条目必须全部重算**，否则新旧向量不在同一空间，相似度是随机的。本库 762 条重算耗时 1.9 秒，可接受；十万条要按批跑。
- **`onnxruntime` 的版本敏感**：`transformers` 3.x 与 4.x 的 runtime 目录结构不兼容，两个版本目录会并存（本次 3.8.1 与 4.2.0 各一份），迁移/备份时都要带上，别只拷一个。
- **模型目录不放进 git**：22.9 MB 二进制进版本库会让每次 clone 变慢，且 LFS 配额易爆。做法是记**来源 + 校验路径 + 下载命令**，让新机器自己下。
